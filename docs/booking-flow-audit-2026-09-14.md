- 未呼叫 Google Maps；未測試真實建單、扣款、優惠券建立或排班寫入。

## 後台原生流程

1. 選服務類別，電話查會員：`/ajax/get_member`。
2. 查無會員才呼叫 `/ajax/create_member`，成功後重新查會員。
3. 選既有地址：沿用該地址 ID、縣市區、區域、座標及清潔資料。新地址：填目前表單縣市區及完整地址。
4. 原生「查詢地區」先使用瀏覽器 Google Geocoder，成功後才 POST `/ajax/check_contain`，參數為 `memberId/cleanTypeId/address/lat/lng/_token`。這與直接送空座標不是相同流程。
5. 「計算時數」POST `/ajax/calculate_hour`，資料是當下整張表單的 `.serialize()`；回填 `data.hour/price/price_vvip/fare`。變更時數後，後台 JS 同步選擇該時數的時段。
6. 「查詢班表」POST `/ajax/get_section`，同樣送當下表單。回覆各筆 `date/section/cleaner`，只有真正回傳的目標日期時段可以選。
7. 選目標時段，填付款／發票（依路由），再送出。成單後核對新訂單及實際日期、時段、地址與人時。

| 項目 | 信用卡／ATM | 儲值金 |
|---|---|---|
| 預訂路由 | `/booking/single` | `/booking/stored_value_routine` |
| 時段選項 | radio `datePeriod` | checkbox `date_list[]` |
| 付款 | `payway=1/2` | `payway=4` |
| 發票 | 依表單選擇 | 原生表單無一般付款發票欄位 |
| 送單 | 原生表單 POST | AJAX POST |
| 結果 | 核對後台回覆及新訂單 | JS 明確以 `count=0` 表示沒有未成立訂單；`count>0` 是未成立筆數 |

## 已確認的程式差異／風險（不是空班表根因結論）

1. `quick_create_order` 的 `_booking_count_success` 用 `count>0` 當成功，與儲值金後台 JS 相反；`_booking_balance_error` 的 count 解釋也需修正。HTTP 200 不可直接等同成單成功。
2. `_find_matching_order_after_submit` 找不到新編號時仍可能回傳送出前已存在的訂單；多個候選編號也有取最後一筆的 fallback。這不足以確認「本次」成單。
3. 共用地址函式目前以空座標直接呼叫後台；它未重現原生 Geocoder → check_contain 流程。不能把移除攔截當作已完成地址查詢。
4. 單筆計時後仍以平日600／週末700公式覆蓋後台 price；這不是純粹回填後台結果。需與既有補價差計價規則分開確認，不能再一併猜改。
5. 新客遇到舊會員的暫存只保留第一筆日期設定；多筆輸入仍需完整逐筆接續，避免遺漏。
6. 批次外層補班後會重跑整組；需證明已成功列不會再次送出，不能只看「無班表」字串就重送全組。
7. 空班表 `[]` 本身無法區分請求資料問題與真正無人；目前自動補班會在根因未明時增加檸檬人班次。
8. 先前已補的上3班與上4班未撤回。不能因為本次未成單就逕自刪班，必須先確認是否已被其他訂單使用。

## 修正與驗收順序

1. 成功請求已重現；下一步查清原始失敗新地址如何取得後台 area_id/company_id。不能借用其他地址編號，也不能因 country_id 有值就假定查詢條件已完整。
2. 建立付款路由明確的共用表單組裝與回覆解析，保留原生日期選擇欄位、付款／發票差異。
3. 訂單時段與補班時段只來自同一筆預約：08:30–12:30→上4；09:00–12:00→上3。有足夠可選人員時不補班。
4. 補班須記錄此次新增、已存在及衝突的結果；查詢錯誤不能當無人，不能反覆加人。
5. 核對本次新訂單，不用舊訂單或任意候選兜底；結果不明時先查證，避免自動重送。
6. 補價差及轉換的會員／帳務步驟獨立保留，所有新單使用上述核心；成功後才進下一階段。
7. 驗證後再提供可審查差異；本輪不沿用「模擬測試過了就直接合併」的做法。

## 取得實際 cURL 後的控制變因結果

以下每次只查 `/ajax/get_section`，不建立訂單，不補班，不呼叫 Google。

| 請求 | HTTP | 回傳時段數 | 9/26 09:00–11:00 |
|---|---:|---:|---|
| 使用者成功請求（只替換有效登入 token） | 200 | 90 | 有 |
| 只清空 area_id | 200 | 0 | 無 |
| 只清空 company_id | 200 | 0 | 無 |
| 只清空 lat、lng，保留兩個區域欄位 | 200 | 90 | 有 |

結論限於此已控制的請求：area_id 與 company_id 缺失各自都會令後台回空陣列。先前失敗訊息確有兩個欄位缺失，這是必須處理的查詢條件，不是可直接用來觸發補班的人力資訊。

這筆成功範例有會員既有地址與服務區域；它不證明原始另一個新地址可以沿用相同區域編號。新地址的原生流程仍是 geocoder → check_contain，尚未取得原始失敗新地址的成功區域查詢證據。

## 已合併的防誤補班修正（PR #69）

- `orders._checked_booking_sections_response`：同時保護批次和單筆查班表。後台回 `[]` 且服務區域欄位缺失時，明確回報查詢資料問題；不進入補班或送單。
- HTTP／登入／JSON 回覆錯誤不再轉成空字串而誤認人力不足。
- 若後台已回可選時段，繼續尊重後台結果；不因空座標另行拒絕。
- 28項本機測試通過；測試不呼叫後台寫入。已合併且同步工作成功，未宣稱原始新地址已可成單。

## 完整四步請求的唯讀重現

使用新登入憑證重現使用者提供的既有地址範例；未儲存使用者提供的 cookie，未成單、補班或呼叫 Google。

- `check_contain` 回覆 `return_code=0000`，取得 `area_id` 與 `company_id`。
- `calculate_hour` 送空 hour、price、price_vvip、fare，回傳 hour=2、price=2286、price_vvip=0、fare=0。
- 按使用者提供的下一步請求，保留後台價格與區域，選定 hour=4、person=2、period_s=08:30-12:30、date_s 空白，再呼叫 `get_section`：HTTP 200，共 76 個時段，包含 2026-09-26 08:30-12:30。
- 因此計算建議時數與使用者最後選定時數必須分開；查班表與補班應使用最後選定時段。這筆查詢不需先補班。
- 現行 quick_create_order 已保留選定 hour/period_s，但仍自行重算 price，與此請求不同；不能把該價格差異直接判為空班表根因。
- 原始新地址沒有已存區域與座標的取得方式仍未解決；這個既有地址成功範例不能替代其驗證。
